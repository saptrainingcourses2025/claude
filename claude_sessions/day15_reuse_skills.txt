● Here's the full authentication & authorization briefing, based on the actual
  code in srv/ and db/.

  1. Authentication — custom JWT bearer tokens

  CAP is configured with a custom auth strategy (package.json):

  "auth": { "kind": "custom", "impl": "./srv/auth/jwt-auth.js" }

  srv/auth/jwt-auth.js is the gatekeeper middleware on every request:
  - No Authorization: Bearer … header → request runs as cds.User.Anonymous().
  - Token present but invalid/expired → 401.
  - Valid token → looks up the user in Users by payload.sub, rejects locked 
  users with 403, loads their roles fresh from UserRoles, and builds the
  cds.User with id, roles, and attr.email = loginName.

  Key design point: roles are re-read from the DB on every request, not trusted
  from the token. So lock/role changes take effect on the next request without
  re-login. The roles claim that login puts in the token is effectively unused
  by the middleware — DB is the source of truth.

  srv/auth/jwt.js — token mechanics:
  - HS256, secret from AUTH_JWT_SECRET. Production throws if it's missing; dev
  generates a random per-process secret (so every server restart invalidates all
   tokens in dev).
  - Access TTL 15m, refresh TTL 7d (env-overridable).
  - audience claim separates access vs refresh tokens so a refresh token can't
  be used as an access token.

  2. Token issuance — AuthService (/auth, requires: 'any')

  Public endpoint; each action enforces its own checks:

  Action: login(loginName, password)
  Behavior: Rejects unknown/locked users; bcrypt-compares against
    UserCredentials; increments failedAttempts on failure; resets counter + sets

    lastLoginAt on success; returns access + refresh + expiresIn.
  ────────────────────────────────────────
  Action: refresh(refreshToken)
  Behavior: Verifies refresh token, re-checks user & lock status, issues a new
    access token and rotates the refresh token.
  ────────────────────────────────────────
  Action: register(...)
  Behavior: Public self-signup: creates Users (isLocked = true), bcrypt creds,
    TRAVELLER role, and a Travellers profile. Account stays locked until an
  admin
     unlocks it. Min 8-char password, email-format validated.
  ────────────────────────────────────────
  Action: me()
  Behavior: Returns the current authenticated user's profile + roles.

  Passwords: bcryptjs, cost factor 10 (srv/auth/password.js). Credentials live
  in a separate UserCredentials entity (db/auth.cds), deliberately kept out of
  Users so service projections of Users never leak password hashes — good
  separation.

  3. Authorization — declarative RBAC per service

  Three roles seeded at startup (srv/init/role-init.js): ADMIN, AGENT, 
  TRAVELLER. Enforced via CDS @requires / @restrict:

  Service: AuthService
  Path: /auth
  Guard: requires: 'any'
  Notes: Public; self-guarding actions
  ────────────────────────────────────────
  Service: PublicService
  Path: /public
  Guard: requires: 'any'
  Notes: Destinations: unauthenticated full CRUD (draft-enabled, what we just
    built)
  ────────────────────────────────────────
  Service: CatalogService
  Path: /catalog
  Guard: requires: 'authenticated-user'
  Notes: ADMIN → full; traveller → CRUD on own rows via where userID = 
    $user.email (Travellers) / traveller.userID = $user.email (Addresses,
    TravelledLocations); code lists @readonly
  ────────────────────────────────────────
  Service: UserManagement
  Path: /user-management
  Guard: requires: 'ADMIN'
  Notes: Whole service ADMIN-only: Users/UserRoles +
    lock/unlock/createUser/resetPassword/assign/unassignRole

  The row-level filtering ($user.email) works because jwt-auth.js puts the login
   email into cds.User.attr.email.

  4. Bootstrap

  On server start (srv/server.js → served hook): roles are seeded idempotently,
  and a default admin is auto-created if absent: anubhav@anubhavtrainings.com /
  Welcome1! (ADMIN, unlocked). Additional seed users exist in db/data/*.csv.

  5. Things worth flagging honestly

  - PublicService Destinations is unauthenticated full CRUD. Anyone can
  create/update/delete destination records with no login. We discussed this last
   turn — fine for training, not for production.
